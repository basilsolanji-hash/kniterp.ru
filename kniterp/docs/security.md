# Защита данных knitERP

Что защищает программа сама и что нужно включить на сервере при выпуске. Ключи, пароли и сертификаты в репозиторий не попадают.

## Что делает программа

| Угроза | Защита |
|---|---|
| Перехват трафика | Только HTTPS (HSTS в рабочей среде); cookie сессии `Secure`, `HttpOnly`, `SameSite`. Соединение с SQL Server в рабочей среде — только шифрованное: без него приложение не запускается. |
| Кража копии базы | Пароли — хеш PBKDF2-HMAC-SHA512, 210 000 итераций (D115; старые хеши пересчитываются при входе), ссылки приглашений — SHA-256. Секреты 2FA и ключи сессий зашифрованы AES-256-GCM мастер-ключом, который хранится вне базы. |
| Подбор пароля | 5 ошибок подряд блокируют учётную запись на 15 минут (D25); не больше 10 отправок форм входа в минуту с одного IP (ответ 429). Владелец и Администратор входят с 2FA. Пароли из списков утечек, ряды клавиш и пароль из имени почты не принимаются (D115). Блокировка не закрывает доверенное устройство владельца — подбирающий не выгонит сотрудника (D115). Резервный код гасится одним условным UPDATE. |
| Украденный пароль или забытый открытым браузер | «Безопасность → Пароль и сессии» (D115): смена пароля и «Выйти на всех устройствах» с повторной проверкой текущего пароля и кода 2FA; все сессии закрываются в течение минуты, доверенные устройства забываются, по выбору — отзыв своих токенов API. Сброс пароля по ссылке отзывает токены API пользователя. О смене пароля, выходе везде и подключении 2FA приходит письмо (без ссылок). |
| Перегрузка API | Тело запроса — до 1 МБ, строк в документе — до 500, частей по партиям в строке — до 100; 100 запросов за 5 секунд на токен (D115, D88). |
| Подмена журнала и остатков | Журнал аудита и движения склада только на вставку (триггеры). Каждая запись подписана HMAC-SHA256 цепочкой организации (номер `ChainSeq` и подпись `ChainHash`); ключ подписи выводится из мастер-ключа. Раздел «Проверка целостности» находит изменённые, удалённые и добавленные в обход программы записи — даже если администратор базы отключил триггеры. |
| Документ задним числом | Закрытый период (сервис и триггер базы). |
| Внедрение скриптов, кликджекинг | CSP `script-src 'self'` (встроенных скриптов нет), `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`. Формы защищены антиподделочным токеном. |
| Доступ к чужим данным | Права проверяются на сервере; организация — из сессии, чужая отвечает «не найдено»; области подразделений и складов. |

Ограничения, которые нужно знать:
- Подпись цепочки не обнаруживает удаление **последних** записей, если после них ничего не записано. Поэтому после сверки периода
  запишите отпечаток со страницы «Проверка целостности» (номер и начало подписи последней записи) — например, в акт сверки.
- Записи, сделанные до включения подписи, проверить нельзя — отчёт показывает их число отдельно.
- Кто знает мастер-ключ и имеет доступ к базе, может подделать подпись. Мастер-ключ хранится отдельно от базы и её копий.

## Аварийный доступ (D06)

Если телефон с приложением-аутентификатором потерян:
1. **Резервный код.** Каждый, кто входит с кодом, выпускает 10 одноразовых кодов (профиль → «Вход и резервные коды»;
   после подключения 2FA программа предлагает это сама). Коды хранятся на бумаге отдельно от телефона, в базе — только
   их хеши. Код вводится вместо 6 цифр; использованный больше не действует.
2. **Сброс другим администратором.** Владелец или Администратор в «Пользователях» сбрасывает 2FA с причиной; резервные
   коды тоже сбрасываются. Поэтому в организации нужны минимум двое с правами администратора.
3. **Команда сервера** — когда войти не может никто из администраторов:
   ```bash
   dotnet KnitErp.Web.dll emergency-access --email <почта> --reason "<причина, № акта>" --url https://<адрес программы>
   ```
   Сбрасывает 2FA и резервные коды, снимает блокировку входа и печатает ссылку установки нового пароля (72 часа, один раз).
   Прежний пароль действует, пока не задан новый. Запись «Аварийное восстановление доступа» с причиной попадает в журнал
   аудита всех организаций пользователя. Выполнять — вдвоём, с актом.

## Мастер-ключ

32 случайных байта в Base64. Создать: `dotnet KnitErp.Web.dll new-master-key` (ключ печатается один раз).

- Рабочая среда: передать через секреты сервера — переменная окружения `Security__MasterKey` или хранилище секретов.
  Не класть в `appsettings.json`, в репозиторий, в базу и рядом с резервными копиями базы.
- Сделать копию ключа в сейфе Владельца (бумажная или на отдельном носителе). **Без ключа секреты 2FA не расшифровать**
  (пользователям придётся заново подключить аутентификатор), а подписи журнала — не проверить.
- Смена ключа: новый ключ — в `Security:MasterKey`, прежний — в `Security:PreviousMasterKeys` (через запятую). Старые значения
  читаются прежним ключом, новые пишутся новым. Прежний ключ не удалять, пока в журнале есть записи, подписанные им.
- Разработка: если ключ не задан, создаётся `~/.kniterp/dev-master.key` (в профиле пользователя, вне репозитория).

## Что включить на сервере при выпуске

1. **Шифрование соединения с базой.** В строке подключения не указывать `Encrypt=false`; на SQL Server установить сертификат
   и не использовать `TrustServerCertificate=true` в рабочей среде. Если база на том же сервере и сеть не используется —
   допускается `Security:AllowUnencryptedDatabase=true`.
2. **Шифрование базы на диске (TDE).** В SQL Server Standard 2019+ и Enterprise:
   ```sql
   USE master;
   CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<пароль из сейфа>';
   CREATE CERTIFICATE KnitErpTde WITH SUBJECT = 'knitERP TDE';
   BACKUP CERTIFICATE KnitErpTde TO FILE = 'KnitErpTde.cer'
       WITH PRIVATE KEY (FILE = 'KnitErpTde.pvk', ENCRYPTION BY PASSWORD = '<пароль из сейфа>');
   USE kniterp;
   CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256 ENCRYPTION BY SERVER CERTIFICATE KnitErpTde;
   ALTER DATABASE kniterp SET ENCRYPTION ON;
   ```
   Файлы сертификата и пароль — в сейф, отдельно от резервных копий: без них копию не восстановить.
3. **Шифрование резервных копий.**
   ```sql
   BACKUP DATABASE kniterp TO DISK = 'kniterp.bak'
       WITH COMPRESSION, ENCRYPTION (ALGORITHM = AES_256, SERVER CERTIFICATE = KnitErpTde), CHECKSUM;
   ```
4. **Учётная запись приложения в базе** — без прав `sysadmin` и `ALTER` на таблицы: только чтение и запись данных
   и выполнение миграций отдельной учётной записью на шаге выпуска (`dotnet KnitErp.Web.dll migrate`). Тогда отключить
   триггеры журнала сможет только администратор базы, и это покажет «Проверка целостности».
5. **Обратный прокси** (nginx, IIS): передавать адрес клиента (`X-Forwarded-For`) и включить в приложении
   ForwardedHeaders — иначе ограничение попыток входа по IP увидит один адрес прокси.
6. Регулярно (например, после закрытия месяца) запускать «Проверку целостности» и записывать отпечаток.
