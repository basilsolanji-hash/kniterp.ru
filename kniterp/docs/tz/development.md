# ТЗ: «Разработка» — модели, образцы, технический паспорт изделия — для отдельной (шестой) сессии Claude

Версия 1.0 от 11.10.2026. Исполнитель — шестая сессия Claude, ветка `claude/development`. Решения — **D700–D799**.

Цель: отдел разработки (дизайнер, конструктор, технолог трикотажа) ведёт новую модель от идеи до запуска в производство в одной программе:
эскиз и задание → подбор пряжи и вязки → образец и его доработки → согласование с заказчиком → расчёт себестоимости и цены →
передача в производство готовой техкарты и позиции каталога. Сейчас это живёт в тетрадях, мессенджерах и Excel — теряются версии,
замеры, причины доработок и сроки.

## 0. Правила совместной работы (обязательно)
1. Ветка от актуальной базы:
   ```
   git fetch origin claude/fervent-volta-3pn88r
   git checkout -B claude/development origin/claude/fervent-volta-3pn88r
   ```
   В чужие ветки не пушить; готовые этапы сливает в базу сессия № 1. Перед каждым этапом: `git fetch origin && git merge origin/claude/fervent-volta-3pn88r`.
2. Номера решений — только **D700–D799** (раздел «Разработка (D700–D799)» в `docs/decisions.md`). Чужие: D86–D199 база,
   D90–D99 и D400–D499 производство, D200–D299 «Сотрудники», D300–D399 каталог, D500–D599 контрагенты, D600–D699 CRM.
3. Свой код: `Domain/Development`, `Application/Development`, страницы `Components/Pages/Dev*`, миграции с префиксом `Dev…`.
   Применённые миграции не редактируются; SQL вне модели — через `EXEC(N'...')`; конфликт снапшота — обе стороны, затем
   `dotnet ef migrations has-pending-model-changes -p src/KnitErp.Infrastructure`.
4. **Чужой код не переписывать.** Техкарты (`Domain/Production/TechCard.cs`, D63, маршрут D401) — у производства; позиции каталога,
   модификации, цены — у каталога; заказы покупателя — у базы; сделки — у CRM. Разработка **создаёт** их только через их сервисы.
   Нужна правка чужого модуля — раздел «Вопросы к базе» в `docs/sessions/development.md` своей ветки.
5. Значения `TaggedEntity` — **40–49** (`DevModel = 40`, `DevSample = 41`): теги и обсуждения работают на карточках разработки.
6. `CLAUDE.md`: права на сервере через `IAccessGuard`; чужая организация → 404; `rowversion`; аудит каждого изменения; история
   версий и согласований — только вставка; справочники архивируются; один DbContext на вкладку; деньги `decimal(19,4)`,
   количества `decimal(18,6)`; допущения — D7xx.
7. Никаких реальных данных: имена заказчиков, фото людей, телефоны — выдуманные. Фото в тестах — сгенерированные картинки.
8. Каждый этап: код → модульные и интеграционные тесты (SQL Server) → e2e .NET Playwright (`tests/KnitErp.E2ETests`, 1440 и 390 px,
   0 ошибок JS) → переводы be/kk/uz → D7xx → коммит → пуш → отчёт по-русски с «Готовность проекта» и «Следующие 3 шага».
   Скиллы: `kniterp-stage`, `kniterp-tests`, `kniterp-translations`, `kniterp-production` (правила техкарт).
9. Интерфейс компактный (D114); телефон 390 px без горизонтальной прокрутки; технолог часто работает с телефона у машины —
   фото и замеры вводятся с телефона.

## 1. Что уже есть (использовать, не дублировать)
- **Каталог:** позиция `Item` (тип «Готовая продукция»), модификации (размер × цвет), группы, артикул, цены, фото.
- **Техкарта** `TechCard` / `TechCardLine` (производство): версии, материалы и нормы, маршрут этапов (D401). Запуск ПЗ — только по
  утверждённой техкарте.
- **Партии пряжи** (D89), остатки — склад базы; **контрагенты** и **договоры** (D500); **CRM** (D600, своя сессия) — сделки и активность
  «образцы отправлены»; **обсуждения** (D107), **теги** (D103), **задачи**, **права и роли** (D112), печать PDF, Excel.

## 2. Права (D700)
| Код | Смысл | По умолчанию |
|---|---|---|
| `dev.view` | Видеть модели и образцы | Разработчик, технолог, руководитель производства, Владелец, Администратор |
| `dev.edit` | Создавать и менять модели, образцы, замеры, фото | Разработчик, технолог, Владелец |
| `dev.approve` | Утверждать модель к запуску, передавать в производство | Главный технолог, Владелец |
| `dev.cost.view` | Видеть себестоимость и расчёт цены | Главный технолог, Владелец, финансы базы (`finance.price.view`) |
| `dev.settings` | Справочники: стадии, виды вязки, классы машин, причины доработок | Главный технолог, Владелец, Администратор |
Новая роль по умолчанию «Разработчик (технолог)» — через `RoleMatrixP0`; группа «Разработка» в редакторе ролей — по префиксу `dev.` (D112).

## 3. Этап 1 — карточка модели и стадии (D701–D709)
- `DevModel`: номер `М-00001`, название, коллекция / сезон (справочник), категория (свитер, кардиган, шапка, шарф, платье, полотно…),
  целевая аудитория (женское, мужское, детское — для детского отмечать требования ТР ТС 007/2011), заказчик (контрагент, необязательно),
  связанная сделка CRM (необязательно, ссылкой), ответственный разработчик, технолог, плановая дата запуска, приоритет, `rowversion`.
- **Стадии** (настраиваемые, по умолчанию): Идея → Задание на разработку → Подбор пряжи и вязки → Образец → Доработка →
  Согласование → Расчёт себестоимости → Утверждено → Передано в производство; также «Отменено» с причиной.
  История стадий — только вставка (кто, когда, сколько дней). Переход вперёд через «Утверждено» — только `dev.approve`.
- **Задание на разработку:** описание, эскиз и референсы (файлы), размерный ряд (из модификаций каталога или справочника размеров),
  цвета, целевая себестоимость и цена, тираж, срок, особые требования (маркировка, состав, уход).
- **Файлы:** эскизы, фото, лекала (PDF, DXF), программы вязальных машин (файлы Stoll `.sin`, Shima Seiki `.dat`) — хранение по образцу
  `CounterpartyContractFile` (проверка сигнатуры файла, ограничение размера, только своя организация); у каждого файла — версия.
- **Экраны:** «Разработка → Модели» — канбан по стадиям и таблица (отборы: коллекция, стадия, разработчик, заказчик, просрочка);
  карточка модели с вкладками: Задание · Пряжа и вязка · Образцы · Размеры и замеры · Себестоимость · Файлы · Обсуждение.

## 4. Этап 2 — пряжа, вязка, образцы (D710–D719)
- **Пряжа и вязка:** выбор пряжи из каталога (с остатками партий базы — только просмотр), цвет / номер краски, переплетение (справочник:
  гладь, ластик 1×1, 2×2, жаккард, интарсия, косы…), класс машины (gauge), плотность по горизонтали и вертикали (петель/рядов на 10 см),
  усадка после ВТО (%), вес изделия по размерам.
- **Образец** `DevSample`: номер `ОБ-00001` (нумерация внутри модели — «образец № 3»), размер, цвет, пряжа (партия, если взята со
  склада — списание делается обычным складским документом базы «на образцы», ссылка в образце), машина и программа (файл),
  кто вязал, время вязки и сборки (мин), фактический вес, фото, результат: «на доработку» / «принят» / «отклонён».
- **Доработки:** причина (справочник: размер, плотность, цвет, посадка, дефект, пожелание заказчика), что меняем, кто, срок.
  Каждая доработка порождает следующий образец; сравнение образцов рядом (замеры, вес, фото).
- **Образец у заказчика:** «передан» (кому, когда, вернуть до), «возвращён», «оставлен у заказчика / продан» — напоминание в колокольчик
  о невозвращённых. Связь с CRM: при передаче — активность «образцы отправлены» в связанной сделке (через сервис CRM, когда он будет;
  до этого — только запись в образце).

## 5. Этап 3 — размеры и замеры (D720–D729)
- **Табель мер** модели: точки измерения (справочник: длина изделия, ширина груди, длина рукава, ширина горловины…), значения по
  размерам, допуск ± см. Шаблон табеля по категории.
- **Замеры образца:** факт по каждой точке, отклонение от табеля, выход за допуск — красным. Ввод с телефона одной колонкой.
- **Градация:** правила приращения между размерами (+ см на размер) — заполнение табеля по базовому размеру.
- Печать «Технический паспорт изделия» (tech pack): эскиз, фото, пряжа и вязка, табель мер, особенности обработки, ВТО, маркировка
  и уход, упаковка — PDF тем же механизмом печати, что УПД.

## 6. Этап 4 — себестоимость и цена (D730–D739)
- **Расчёт себестоимости модели** (видно с `dev.cost.view`): пряжа (вес изделия × (1 + отходы %) × цена пряжи из каталога / последней
  закупки), фурнитура и упаковка (позиции каталога), работа (минуты по этапам маршрута × расценки — читать расценки модуля «Сотрудники»
  только через их сервис/контракт, если он есть; иначе ставка за минуту из настроек разработки), накладные расходы (% из настроек).
- **Цена:** наценка или целевая цена → маржа; сравнение с целевой себестоимостью из задания. Версии расчёта — только вставка.
- Сценарии: «а если другая пряжа» — копия расчёта с заменой материала.

## 7. Этап 5 — передача в производство (D740–D749)
- Кнопка «Передать в производство» (только `dev.approve`, стадия «Утверждено»), одна транзакция через сервисы владельцев:
  1. **Каталог:** создать позицию «Готовая продукция» и модификации (размер × цвет) или привязать существующие; фото и состав.
  2. **Производство:** создать черновик техкарты на каждую модификацию (или общую) — материалы и нормы из расчёта, маршрут этапов,
     программа машины файлом; утверждает техкарту производство своим порядком.
  3. Модель → «Передано в производство», ссылки на позиции и техкарты; дальнейшие изменения — новой версией модели.
- Точки соприкосновения согласовать заранее в «Вопросах к базе» (производству и каталогу через их файлы `docs/sessions/*.md`):
  метод создания черновика техкарты, метод создания позиции с модификациями.

## 8. Этап 6 — аналитика (D750–D759)
- Отчёты: модели по стадиям и срокам (просрочка), среднее время разработки, число образцов на модель, причины доработок,
  загрузка разработчиков, принятые / отклонённые заказчиком, план-факт себестоимости (разработка против фактической себестоимости
  первых производственных заказов — из отчёта производства, только чтение). Excel.
- Главный экран: блок «Разработка» (в работе, просрочено, образцы у заказчиков) — интерфейс `IDevelopmentDashboardSource`
  по образцу `IProductionDashboardSource`; блок добавит база по запросу.

## 9. Нефункциональные требования
- Файлы — до 50 МБ (программы машин, лекала), фото сжимаются на сервере до 2000 px; доступ к файлу — только через проверку прав.
- Списки — постраничные проекции; канбан — не больше 5 запросов; `rowversion` и понятное сообщение о конфликте.
- Время — в поясе организации (`TimeZones.ToLocal(utc, CurrentAccess.TimeZoneId)`, не `ToLocalTime()`).
- Все строки — `L("…")`; сообщения `BusinessRuleException` — с переводами.
- Статьи модуля для помощника — `Knowledge/dev-*.json`, `id` с префиксом `dev-`, рубрика «Модуль · Разработка» (ТЗ помощника, § 4.5).

## 10. Приёмка этапа
Модульные (стадии и переходы, допуски замеров, градация, расчёт себестоимости и маржи) и интеграционные тесты (чужая организация → 404,
без `dev.approve` нельзя утвердить и передать, история стадий и версий только вставка, файл чужой организации недоступен, передача
в производство — одна транзакция), e2e: модель → образец → доработка → второй образец с замерами → утверждение → передача →
позиция каталога и черновик техкарты созданы; телефон 390 px; 0 ошибок JS. Отчёт — по-русски, с «Готовность проекта» и «Следующие 3 шага».
