# ТЗ: проверка интерфейса всех экранов knitERP и правки — удобно, безопасно, быстро, современно

Версия 1.0 от 12.10.2026. Исполнитель — отдельная сессия Claude, ветка `claude/ui-review`. Номера решений — **D800–D899**.

## 0. Требования владельца 13.10.2026 — главное в этом ТЗ (делать первыми, в этом порядке)
1. **Меню — пересмотреть кардинально, чтобы было удобно.** Сейчас длинный список разделов с вложенными пунктами (CRM раскрывается
   на 15 строк, есть пункты «скоро»). Нужно: группы по работе пользователя (Продажи, Закупки, Склад, Производство, Деньги, Сотрудники,
   CRM, Разработка, Справочники, Настройки), в группе — 3–7 частых пунктов, редкие — на странице раздела; одна раскрытая группа;
   пункты «скоро» убрать из меню; поиск по меню (Ctrl+K уже есть — показать подсказку); избранное/частые пункты пользователя сверху;
   на телефоне — нижняя панель 4–5 главных разделов + «Ещё». Видимость по правам — как сейчас (`Allowed`). Прежде чем делать —
   опись текущего меню и схема нового в `docs/ui/menu.md` с обоснованием, затем реализация.
2. **Верхняя панель — без скрытых значков.** Все значки по умолчанию видны и расставлены в разумном порядке (поиск, создать, уведомления,
   задачи, календарь, калькулятор, заметки, помощник); никаких «спрятанных в настройках» по умолчанию; на телефоне — те же главные
   значки, остальное в одном меню «Ещё». У каждого значка — подпись при наведении и `aria-label`. Настройка панели пользователем
   остаётся, но умолчание должно быть сразу удобным.
3. **Блок пользователя (внизу меню и профиль) — переделать.** Сейчас: имя, роль, «Рабочий день» с полосами, «Обучение», «Поддержка».
   Нужно: компактный блок — аватар/инициалы, имя, организация и роль; по нажатию — меню: профиль и пароль, сессии и устройства,
   помощник (Ника/Книт/без), тема, размер интерфейса, язык, обучение, поддержка, выход. «Рабочий день» — свернуть в одну строку
   (время и задачи) или перенести на главную. Ничего важного не терять.
4. **Все экраны пересмотреть:** порядок блоков и полей (главное сверху), видимость (не показывать то, что не нужно этой роли и
   этому контрагенту), кнопки (одна главная кнопка на экран, остальные — второстепенные или в меню «…»), экономия места (плотные
   таблицы, фильтры свёрнуты на телефоне, без пустых отступов), контраст (WCAG AA: текст 4,5:1, светлая и тёмная тема), современный
   единый вид (одни отступы, радиусы, размеры шрифтов, иконки одного набора). Результат по каждому экрану — строка в
   `docs/ui/findings.md` «было → стало» и снимки 1440/390 px.

**Разделение работы (чтобы не править одни файлы):** `MainLayout.razor`, меню, верхняя панель, блок пользователя, общие стили и
компоненты (`Shared/*`, `App.razor`) — только сессия интерфейса. Экраны «Разработки» (`Dev*.razor`) по пункту 4 пересматривает сама
сессия «Разработка» по этому же чек-листу (её предложение для меню: частые — Модели, Мои задачи разработки, Библиотека рисунков,
Техкарты вязания, Станки и программы; Аналитику и Настройки — на страницу раздела). Остальные экраны — сессия интерфейса.

## 1. Цель
Пройти все экраны программы (около 110 страниц и панелей) глазами пользователя фабрики — владельца, бухгалтера, кладовщика,
мастера цеха, менеджера — на компьютере и телефоне, найти всё, что мешает, и исправить. Итог: единый, понятный, быстрый и
безопасный интерфейс без изменения бизнес-правил.

## 2. Правила совместной работы (обязательно)
1. Ветка от актуальной базы:
   ```
   git fetch origin claude/fervent-volta-3pn88r
   git checkout -B claude/ui-review origin/claude/fervent-volta-3pn88r
   ```
   Перед каждой партией правок: `git fetch origin && git merge origin/claude/fervent-volta-3pn88r`. Сливает в базу сессия № 1.
2. **Что можно менять:** разметку `.razor`, стили (`App.razor`, CSS), тексты интерфейса и переводы, порядок полей и кнопок,
   доступность (aria, фокус, клавиатура), загрузку данных на странице (последовательно, без параллельных запросов в один DbContext).
3. **Что нельзя:** правила и проверки в сервисах `Application`/`Domain`, права, миграции, API. Нужна правка логики — запишите
   в `docs/sessions/ui.md` (раздел «Вопросы к модулям»): владелец модуля сделает сам. Модули: база (сессия № 1), производство,
   «Сотрудники», каталог, контрагенты, CRM, «Разработка».
4. Правки в экранах модулей других сессий — небольшими коммитами по одному модулю, с пометкой модуля в сообщении коммита и
   записью в `docs/sessions/ui.md` — чтобы владельцы при слиянии видели, что изменилось.
5. Номера решений — D800–D899. Чужие: D86–D199 база, D90–D99 и D400–D499 производство, D200–D299 «Сотрудники», D300–D399 каталог,
   D500–D599 контрагенты, D600–D699 CRM, D700–D799 «Разработка».
6. `CLAUDE.md`: скрытая кнопка — не защита (проверка на сервере остаётся), один DbContext на вкладку, никаких реальных
   персональных данных в тестах и снимках экрана.
7. Каждая партия: правки → модульные и интеграционные тесты → сквозные .NET Playwright (`tests/KnitErp.E2ETests`) → переводы
   be/kk/uz (`TranslationCoverageTests`) → решения D8xx → коммит → пуш → отчёт по-русски с «Готовность проекта» и «Следующие 3 шага».
   Скиллы: `kniterp-e2e`, `kniterp-tests`, `kniterp-translations`, `kniterp-stage`.

## 3. Этап 1 — опись экранов (D800)
Таблица `docs/ui/screens.md`: адрес, название, модуль-владелец, роли, которые его видят, главные действия, есть ли версия для телефона.
Источник — `@page` в `Components`, меню `MainLayout`, панели инструментов. Снимки каждого экрана: 1440 px и 390 px, светлая и
тёмная тема, роли Владелец и Кладовщик (папка артефактов e2e, в репозиторий не кладутся).

## 4. Этап 2 — проверка по чек-листу (D801–D809)
Для каждого экрана — оценка по пунктам; находка — строка в `docs/ui/findings.md`: экран, пункт, что не так, важность
(блокирует / мешает / косметика), снимок, предложение.

### 4.1. Удобство
- Главное действие видно сразу, одно основное (цвет), остальные — второстепенные; порядок кнопок одинаков на всех экранах
  («Сохранить» справа или первым — как принято в базе, D38/D108).
- До любого действия — не больше 3 нажатий из меню; хлебные крошки или «Назад» на карточках.
- Формы: поля в порядке заполнения, значения по умолчанию, автофокус на первом поле, подписи у каждого поля, единицы измерения
  рядом, обязательные отмечены, ошибки — у поля и понятным языком, ввод не теряется при ошибке.
- Пустые состояния: что это за экран и одна кнопка «Создать первый…».
- Списки: поиск, фильтры, сортировка, итоги, постраничность; выбранные фильтры видны и сбрасываются одним нажатием.
- Длинные операции: индикатор, кнопка блокируется до ответа (D29), итог — сообщением «успех» только после ответа сервера.
- Тексты: одна терминология во всей программе (словарь терминов — `docs/ui/glossary.md`), без внутренних кодов и английских слов.

### 4.2. Безопасность в интерфейсе
- Кнопки и разделы, на которые нет права, скрыты (сервер всё равно проверяет); в DOM и ответах нет данных, которые пользователю не положены.
- Опасные действия (удаление, сторно, отмена, блокировка, выдача прав) — с подтверждением и причиной; необратимость названа прямо.
- Пароли, токены, коды: `type="password"`, `autocomplete` по назначению, токен показывается один раз, не попадает в адресную строку,
  журнал браузера и снимки.
- Персональные данные сотрудников (152-ФЗ) — только при праве; в списках — маска, где полное не нужно.
- Внешние ссылки — `rel="noopener noreferrer"`; загрузки файлов — проверка типа и размера с понятным сообщением.
- Нет встроенных скриптов (CSP `script-src 'self'`), нет `MarkupString` с пользовательским текстом.

### 4.3. Скорость
- Первая отрисовка любого экрана — до 1 с на тестовых данных, список 10 000 строк — постранично и без зависания.
- Число SQL-запросов на открытие экрана (перехватчик EF в e2e): цель — не больше 10; лишние повторные загрузки убрать.
- Тяжёлые блоки — после первой отрисовки; изображения — WebP, с размерами; на телефоне не грузить скрытое.

### 4.4. Современно и доступно
- Компактный вид по умолчанию (D114), крупный — по настройке; телефон 390 px без горизонтальной прокрутки и перекрытий.
- Тёмная тема без «белых пятен» и нечитаемых цветов; контраст не ниже WCAG 2.2 AA (4,5:1 для текста).
- Клавиатура: всё доступно с Tab, видимый фокус, Enter/Escape в диалогах, горячие клавиши не конфликтуют с браузером.
- Скринридер: `aria-label` у иконок-кнопок, роли у вкладок и диалогов, `role="alert"` у ошибок, заголовки по порядку.
- «Уменьшить движение» в системе — без анимаций.
- Числа, деньги, даты — в формате пользователя, выравнивание чисел по правому краю, разделители разрядов.

## 5. Этап 3 — исправления (D810–D889)
Партиями по разделам в порядке важности находок: вход и профиль → главный экран и меню → продажи → закупки → склад → деньги →
производство → сотрудники → каталог → контрагенты → настройки и администрирование → отчёты → CRM и «Разработка» (когда появятся).
Общие проблемы — правкой общих компонентов (`Shared/*`, стили), а не на каждой странице отдельно. Каждая партия — свои e2e-проверки
(в том числе отсутствие горизонтальной прокрутки на 390 px и 0 ошибок JS на всех экранах раздела).

## 6. Этап 4 — защита от возврата ошибок (D890–D899)
- Сквозной тест «обход всех экранов»: каждый адрес из описи открывается Владельцем на 1440 и 390 px без ошибок JS, без
  горизонтальной прокрутки, с заголовком `h1` и без текста «Exception».
- Тест доступности: проверка axe-core (локальной копией скрипта, без внешних CDN) на каждом экране — без нарушений уровня «serious».
- Правила для всех сессий — `docs/ui/guidelines.md`: сетка, кнопки, формы, таблицы, пустые состояния, сообщения, телефон.

## 7. Приёмка
Все находки «блокирует» и «мешает» исправлены или переданы модулю с записью; тест обхода всех экранов и тест доступности — зелёные;
модульные, интеграционные и e2e тесты — зелёные; отчёт владельцу по-русски: что найдено, что исправлено (с парами снимков
«до/после»), что передано модулям, «Готовность проекта» и «Следующие 3 шага».

## Дополнение 13.10.2026 (сессия № 1): известные находки — сразу после раздела 0
1. **Ввод до подключения страницы теряется.** Поле, заполненное в первые 1–2 с после открытия (до подключения Blazor), сбрасывается,
   а «Сохранить» сохраняет прежнее значение и пишет «сохранено» (воспроизведено: «Настройки закупок», «Сменные задания», формы
   контрагентов). На телефоне в цеху это реальная потеря данных. Сделать общим решением: до подключения поля и кнопки форм
   недоступны (или видна полоса «Подключение…»), после — включаются. Проверка e2e: ввод сразу после открытия сохраняется.
2. **Мигание «Загрузка…» ~0,5 с на главной** после первого показа (аудит 12.10) — сохранить состояние между предрисовкой и
   подключением (`PersistentComponentState`) или показать каркас блоков вместо текста.
3. **Неактивные кнопки без объяснения** — у каждой `disabled` кнопки подсказка «почему» (`title` и текст рядом на телефоне).
4. **Зоны нажатия на телефоне** меньше 44 px на страницах «Скидки и акции», «Этикетки», в таблицах документов — довести до 44 px.
5. **Карточка контрагента:** у чистого поставщика видны вкладки продаж («Условия продаж», «Почта для документов»), у чистого
   покупателя — «Расчёты с поставщиком». Показывать вкладки по роли контрагента (покупатель/поставщик); логику модулей не менять.
6. **Даты по умолчанию в формах** — сегодня по часовому поясу организации, где дата обязательна (образец — вкладка
   «Расчёты с поставщиком», D133).
7. Не ломать: страница стартует только после всех запросов меню (`MainLayout`, `_access` присваивается последним, аудит 13.10).
