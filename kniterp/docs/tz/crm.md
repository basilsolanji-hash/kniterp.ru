# ТЗ: CRM — лиды, сделки, контакты, активности — для отдельной (пятой) сессии Claude

Версия 1.0 от 11.10.2026. Исполнитель — пятая сессия Claude. Параллельно работают:
- сессия № 1 — база: склад, продажи, закупки, деньги, API, теги, обсуждения, главный экран, права (`claude/fervent-volta-3pn88r`);
- производство (`claude/kniterp-repository-study-2u528m`), «Сотрудники» (`claude/hr-employees`), каталог (`claude/catalog-products`);
- контрагенты и договоры, удобство интерфейса (`claude/fervent-gates-248buc`).

Цель: менеджер видит всех потенциальных и текущих покупателей фабрики, ведёт их по воронке от первого обращения до заказа
покупателя и повторной продажи; руководитель видит воронку, конверсию, план и факт. CRM — часть knitERP, а не отдельная программа:
сделка превращается в заказ покупателя базы, деньги и отгрузки видны в сделке из базы, без двойного ввода.

## 0. Правила совместной работы (обязательно)
1. Своя ветка от актуальной базы:
   ```
   git fetch origin claude/fervent-volta-3pn88r
   git checkout -B claude/crm origin/claude/fervent-volta-3pn88r
   ```
   В чужие ветки не пушить. Сессия № 1 сама сливает готовые этапы в базу (владелец разрешил всегда); перед каждым этапом
   подтягивайте базу: `git fetch origin && git merge origin/claude/fervent-volta-3pn88r`.
2. Номера решений в `docs/decisions.md` — **только D600–D699** (отдельный раздел «CRM (D600–D699)»). Чужие: D86–D199 база,
   D90–D99 и D400–D499 производство, D200–D299 «Сотрудники», D300–D399 каталог, D500–D599 контрагенты и договоры.
3. Свой код: `Domain/Crm`, `Application/Crm`, страницы `Components/Pages/Crm*`, миграции с префиксом `Crm…`
   (`dotnet ef migrations add CrmLeads -p src/KnitErp.Infrastructure -o Persistence/Migrations`). Применённые миграции не редактируются;
   SQL вне модели — через `EXEC(N'...')`. Конфликт в `KnitErpDbContextModelSnapshot.cs` при слиянии базы — принять обе стороны и
   проверить `dotnet ef migrations has-pending-model-changes -p src/KnitErp.Infrastructure`.
4. Чужой код не переписывать. Точки соприкосновения — только перечисленные в п. 9 и каждая с тестом и пометкой в коммите:
   - `SalesService` (создание заказа покупателя из сделки) и `Counterparty` — база и сессия контрагентов;
   - главный экран — через интерфейс источника данных (как `IProductionDashboardSource`), не правкой `DashboardService` целиком.
   Нужна правка в чужом модуле — напишите в `docs/sessions/crm.md` своей ветки, раздел «Вопросы к базе»: сессия № 1 читает его перед каждым слиянием.
5. Значения `TaggedEntity` для CRM — **30–39** (`Lead = 30`, `Deal = 31`, `Contact = 32`). Тогда теги и обсуждения (D103, D107)
   работают на карточках CRM без доработок базы — допишите только видимость объекта в `DiscussionService`/теги через свой сервис (п. 9).
6. Соблюдать `CLAUDE.md`:
   - права на сервере через `IAccessGuard`;
   - организация берётся из сессии, чужое → 404;
   - `rowversion` на изменяемых сущностях;
   - журнал аудита на каждое изменение, журнал и история этапов — только вставка;
   - справочники не удаляются, а архивируются;
   - один DbContext на вкладку Blazor;
   - допущения помечаются как D6xx.
7. Никаких реальных телефонов, почт, имён клиентов, токенов в коде и тестах — только выдуманные (`+7 900 000-00-01`, `test@example.org`).
8. Каждый этап: реализация → модульные и интеграционные тесты (SQL Server) → e2e на .NET Playwright (`tests/KnitErp.E2ETests`,
   1440 px и 390 px, 0 ошибок JS) → переводы be/kk/uz (`TranslationCoverageTests`) → решения D6xx → коммит → пуш → отчёт по-русски
   с разделами «Готовность проекта» и «Следующие 3 шага». Порядок и проверки — скиллы `kniterp-stage`, `kniterp-tests`, `kniterp-translations`.
9. Интерфейс — компактный (D114): высоту касания задают общие правила, без фиксированных 44 px; телефон 390 px без горизонтальной прокрутки.

## 1. Что уже есть в базе (использовать, не дублировать)
- **Контрагент** `Counterparty` (`Domain/Catalog/Counterparty.cs`): наименование, страна, ИНН/КПП, адрес, роли «покупатель»/«поставщик»,
  архив; карточка контрагента с договорами `CounterpartyContract` (сессия контрагентов, D500). CRM **не заводит свою «компанию»**:
  компания в CRM = контрагент. Лид без реквизитов создаёт контрагента только при квалификации (п. 3).
- **Заказ покупателя** `SalesOrder`: этапы `SalesOrderStage` и автосмена этапа (D110), проект и канал продаж (справочник `Lookup`,
  `LookupKind.Project`/`SalesChannel`), ответственный `ResponsibleUserId`, скидки, резерв, счета, оплаты, отгрузки.
- **Теги** (D103–D104), **обсуждения** с упоминаниями (D107), **задачи и заметки** пользователя (`PersonalToolsService`),
  **уведомления** и колокольчик, **API v1** с токенами, идемпотентностью и вебхуками (D88, D102), **свои роли и права** (D112),
  **импорт/экспорт Excel** (ClosedXML), **журнал аудита**.
- **Помощник** (D116) — CRM в него не встраивается до отдельного решения владельца.

## 2. Права (D600)
Новые права с префиксом `crm.` — группа «CRM» в редакторе ролей появится сама (`Permissions.GroupOf`, D112). Дописать в
`Permissions.Labels` и `RoleMatrixP0`.

| Код | Смысл | По умолчанию |
|---|---|---|
| `crm.view` | Видеть лиды, сделки, контакты, где пользователь ответственный или участник | Менеджер продаж, руководитель продаж, Владелец, Администратор |
| `crm.edit` | Создавать и менять свои лиды, сделки, контакты, активности | Менеджер продаж, руководитель продаж, Владелец |
| `crm.all` | Видеть и менять **все** лиды и сделки организации, переназначать ответственного | Руководитель продаж, Владелец |
| `crm.settings` | Воронки, этапы, причины отказа, источники, поля, план продаж | Руководитель продаж, Владелец, Администратор |
| `crm.export` | Выгрузка в Excel (персональные данные контактов) | Руководитель продаж, Владелец |

Без `crm.all` чужая сделка → 404 (как чужая организация). Сумма сделки и деньги из базы видны, только если есть право на цены/деньги
базы (`finance.price.view` и права продаж) — иначе «—».

## 3. Этап 1 — лиды и сделки, воронки (D601–D609)
**Лид** — первое обращение, ещё не проверенное: «написали в Telegram про 300 свитеров», заявка с сайта, звонок.
- `CrmLead`: организация, номер `Л-00001` (сквозной по организации), название, источник (справочник `CrmSource`: сайт, звонок,
  выставка, маркетплейс, рекомендация, соцсети…; архивируется), канал продаж базы (`Lookup`), ответственный, контактное лицо
  (имя, телефон, почта, мессенджер — текстом до квалификации), компания текстом, ИНН (необязательно), потребность, ожидаемая сумма и
  валюта, статус `New / InWork / Qualified / Rejected`, причина отказа (справочник), даты, `rowversion`.
- **Квалификация** — одна команда в транзакции: лид → контакт (п. 4) + контрагент (найти по ИНН или по точному названию; иначе создать
  с ролью «покупатель») + сделка. Лид остаётся в истории со ссылками; повторная квалификация запрещена.
- **Дубликаты:** при создании лида и контакта — подсказка «похожие» по телефону (нормализация E.164), почте (нижний регистр) и ИНН;
  объединение лидов — только с `crm.all`, с записью в аудит.

**Сделка** — квалифицированная возможность продажи.
- `CrmDeal`: номер `С-00001`, название, контрагент (обязательно), основной контакт, воронка и этап, сумма и валюта,
  вероятность (по умолчанию из этапа), плановая дата закрытия, ответственный, участники (наблюдатели), проект базы, канал, источник,
  итог `Open / Won / Lost`, причина проигрыша, связанные заказы покупателя (0..n), `rowversion`.
- **Воронки** `CrmPipeline` (несколько: «Опт», «Маркетплейсы», «Пошив по ТЗ клиента») и **этапы** `CrmStage` (порядок, цвет,
  вероятность %, признак «выигрыш»/«проигрыш»; не удаляются — архивируются; у воронки ровно один этап «выигрыш» и один «проигрыш»).
  Готовая воронка при создании организации: «Новая → Выявление потребности → Образцы / расчёт → КП отправлено → Согласование →
  Выиграна / Проиграна».
- **История этапов** `CrmDealStageHistory` — только вставка: кто, когда, с какого на какой, сколько дней провела на этапе.
- **Сделка → заказ покупателя:** кнопка «Создать заказ» вызывает `SalesService` базы (контрагент, проект, канал, ответственный,
  строки по позициям каталога из сделки, если указаны). Заказ хранит ссылку на сделку (`SalesOrder.CrmDealId`, nullable — точечное
  поле, согласовать в «Вопросах к базе»). Подтверждённый заказ по сделке → сделка «Выиграна» автоматически (если этап не финальный).
- **Экраны:** «CRM → Сделки» — канбан по этапам (перетаскивание мышью и кнопками «←/→» для телефона и клавиатуры) и таблица;
  фильтры: воронка, ответственный, источник, тег, дата закрытия, «мои / все»; итог суммы по колонке. «CRM → Лиды» — таблица и
  быстрый ввод в одну строку. Карточки лида и сделки: шапка, этап-лента, активности (п. 5), обсуждение, теги, связанные заказы
  с их этапом, суммой, оплатой и отгрузкой (только чтение, из базы).

## 4. Этап 2 — контакты и согласия (D610–D619)
- `CrmContact`: ФИО, должность, контрагент (необязательно, у одного контакта — одна основная компания), телефоны и почты (несколько,
  с видом и признаком «основной»), мессенджеры (Telegram, WhatsApp, VK — как ссылка/имя пользователя), день рождения
  (необязательно), комментарий, ответственный, архив.
- **Персональные данные (152-ФЗ):**
  - основание обработки и дата: «договор / заявка клиента», «согласие» (с датой и способом получения), «иное» с пояснением;
  - **согласие на рассылки** — отдельный флажок с датой (ст. 18 38-ФЗ «О рекламе»), по умолчанию выключен; без него контакт не
    попадает ни в какие рассылки и выгрузки для рассылок;
  - «Удалить персональные данные по запросу» (`crm.all`): ФИО, телефоны, почты заменяются на «удалено по запросу» с датой; сделки,
    суммы и история остаются; запись в аудит;
  - выгрузка контактов в Excel — только с `crm.export`, факт выгрузки — в аудит;
  - в журнал аудита изменений не пишутся значения телефонов и почт полностью — маска (`+7 900 ***-**-01`).
- Карточка контрагента базы: вкладка «Контакты и сделки» — подключается через небольшой компонент CRM, который карточка показывает,
  если у пользователя есть `crm.view` (согласовать точку встраивания в «Вопросах к базе»).

## 5. Этап 3 — активности и лента (D620–D629)
- `CrmActivity`: вид (звонок, встреча, письмо, задача, образцы отправлены, КП отправлено, заметка), объект (лид / сделка / контакт),
  тема, текст, срок, исполнитель, результат, «выполнено» с датой. Изменения — с аудитом; выполненную нельзя «отменить» без следа.
- **Лента** на карточке: активности + смены этапа + заказы, счета, оплаты, отгрузки базы по связанным заказам + комментарии
  обсуждения — одна хронология, подгрузка порциями по 50.
- **Напоминания:** просроченные активности и «сделка без следующего шага» (открытая сделка без запланированной активности) —
  в колокольчик ответственного и в блок «Мои задачи CRM».
- **Правила следующего шага** (по этапу): при переходе на «КП отправлено» предложить задачу «Позвонить через 3 дня» — настраивается
  в `crm.settings`, по умолчанию включено для 2 этапов. Только предложение — пользователь подтверждает.
- КП: печатная форма «Коммерческое предложение» (позиции каталога, цены выбранного вида цен, условия, срок действия) — HTML и PDF
  тем же механизмом печати, что УПД; фиксируется как активность «КП отправлено» с номером и суммой.

## 6. Этап 4 — аналитика и план (D630–D639)
- Отчёты: **воронка** (количество и сумма по этапам, конверсия этап → этап и лид → сделка → выигрыш), **скорость** (среднее время на
  этапе, цикл сделки), **причины проигрыша**, **источники** (лиды, выигрыши, выручка по оплаченным заказам базы),
  **менеджеры** (активности, сделки, выигрыши, сумма). Период, воронка, ответственный; Excel-выгрузка.
- **План продаж** на месяц по менеджеру/воронке (`crm.settings`), факт — сумма выигранных сделок или оплаченных заказов базы
  (выбор в настройках, по умолчанию «оплаты»).
- **Главный экран:** блок «CRM» (сделки в работе и их сумма, взвешенная по вероятности, выигрыш месяца против плана, просроченные
  активности, сделки без следующего шага). Реализовать интерфейс `ICrmDashboardSource` по образцу `IProductionDashboardSource`
  (`Application/Workspace/ProductionDashboard.cs`): сессия № 1 добавит блок `DashboardBlocks.Crm` в базе по вашему запросу
  в «Вопросах к базе»; без прав `crm.view` источник возвращает null.

## 7. Этап 5 — входящие заявки, импорт, интеграции (D640–D659)
- **Заявки с сайта и маркетплейсов** через существующий API v1 (D88): `POST /api/v1/crm/leads` с токеном области `crm.leads.create`,
  идемпотентность по ключу, лимиты, дубликаты по телефону/почте → активность «повторное обращение» к найденному лиду. Вебхуки
  `crm.lead.created`, `crm.deal.won`, `crm.deal.lost`. OpenAPI-описание.
- **Импорт** лидов, контактов и сделок из Excel/CSV с предпросмотром и отчётом ошибок (как импорт номенклатуры), шаблоны под выгрузки
  amoCRM и Битрикс24 (сопоставление столбцов, этапы по названию). Сохранять внешний идентификатор (`crm_external_links`: система,
  внешний id) для повторного импорта без дублей.
- **Почта и телефония — следующий этап, после решения владельца:** подключение ящика (IMAP/SMTP) и IP-телефонии (запись о звонке
  по вебхуку, без хранения записей разговоров в MVP). В этом ТЗ — только модель `CrmActivity`, готовая принять такие события.

## 8. Нефункциональные требования
- Списки и канбан — до 10 000 открытых сделок: постраничная выдача и проекции на сервере, индексы по
  `(OrganizationId, PipelineId, StageId)`, `(OrganizationId, ResponsibleUserId, Outcome)`, `(OrganizationId, Phone/Email нормализованные)`.
  Тест числа запросов на открытие канбана (не больше 5).
- Одновременная правка — `rowversion`, понятное сообщение «Сделку изменил {кто}, обновите».
- Время — в часовом поясе организации; деньги — `decimal(19,4)` (как в `CLAUDE.md`), валюта из справочника базы.
- Все строки интерфейса — `L("…")`, сообщения `BusinessRuleException` — с переводами.

## 9. Точки соприкосновения с базой (согласовать до кода, в «Вопросах к базе»)

3. Вкладка «Контакты и сделки» в карточке контрагента (компонент CRM).
4. `ICrmDashboardSource` и блок главного экрана.
5. Раздел «CRM» в меню и права в `RoleMatrixP0`.

## 10. Приёмка этапа
Модульные (правила воронки, вероятности, квалификации, дубликатов, нормализации телефона, плана) и интеграционные тесты
(организация чужая → 404, без `crm.all` чужая сделка → 404, история этапов только вставка, квалификация в одной транзакции,
согласие на рассылку, удаление ПДн), e2e: лид → квалификация → сделка → канбан → заказ покупателя → подтверждение → сделка выиграна;
телефон 390 px; светлая и тёмная тема; 0 ошибок JS. Отчёт владельцу — по-русски, с «Готовность проекта» и «Следующие 3 шага».
