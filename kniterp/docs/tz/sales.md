# ТЗ: «Продажи» — полная доработка раздела

Версия 1.0 от 12.10.2026. Ветка `claude/sales`, решения D1100–D1199. Заказчик — владелец продукта: сначала работа на своей фабрике
трикотажа, затем продажа knitERP по подписке (`docs/tz/subscription.md`). Всё, что делается, должно работать для любой организации.

## 0. С чего начать
1. `git fetch && git checkout -b claude/sales origin/claude/fervent-volta-3pn88r`. Прочитать `CLAUDE.md`, `docs/mvp-scope.md`,
   `docs/decisions.md` (D49, D105–D119), `docs/sessions/base.md`, `docs/tz/crm.md` (граница с CRM), `docs/automation.md`.
2. Изучить, что уже есть, и не переписывать работающее:
   - `Application/Sales/`: `SalesService` (заказы, строки, подтверждение, отгрузка, возврат, оплаты, распределение, авансы,
     резерв, скидка на заказ, этапы), `CustomerInvoiceService` (счета), `SalesStageService` + `StageAutomation` (D110),
     `SalesAnalyticsService` (продажи по позициям, рентабельность), `SalesSettingsService` (справочники и свои поля), `Reservations`.
   - Каталог: виды цен (`PriceType`), история цен и переоценка (`Trade.cs`), маркировка (`Marking`), фиды (`Feeds.cs`),
     внешние связи с Wildberries и Ozon (`ExternalLinks.cs`).
   - Контрагенты и договоры: `CounterpartyContract.PaymentDays` (отсрочка) и `AmountLimit` (лимит) — в продажах пока не применяются.
   - Деньги: выписка банка (D119), УПД и счета-фактуры, журналы выданных счетов-фактур.
   - Права: `sales.document.view`, `sales.document.edit`, `finance.price.view`; роли `SalesManager`, `SalesHead` (из CRM).
3. Составить карту «есть / частично / нет» по разделам 2–11 и положить в `docs/sessions/sales.md` до начала кода.

## 1. Цели
- Менеджер оформляет типовой заказ за 1–2 минуты, повторный — за 30 секунд; ручного ввода — минимум.
- Руководитель видит, что продаётся, кто должен деньги, что отгрузить сегодня и где теряется маржа.
- Никаких отгрузок сверх лимита и продаж ниже допустимой цены без явного разрешения с записью в аудит.
- Документы соответствуют законодательству РФ (УПД, счёт-фактура, ТОРГ-12 по требованию, маркировка «Честный ЗНАК»).

## 2. Цены и соглашения
- Цена в строке заказа подставляется сама: соглашение с клиентом → вид цены клиента (из карточки или договора) → базовый вид цены.
- **Соглашение с покупателем** (новое): контрагент или группа, вид цены, скидка %, срок действия, условия оплаты (предоплата %,
  отсрочка), склад по умолчанию. Действует по датам; история изменений.
- **Минимальная цена / максимальная скидка** по роли: ниже — заказ сохраняется, но подтверждение требует права
  `sales.price.override` (новое) с причиной; запись в аудит.
- Печать прайс-листа по виду цены и отбору (группа, наличие) в PDF и Excel; ссылки на картинки — по правам каталога.

## 3. Скидки и акции
- Скидки: ручная на строку и на заказ (есть), по соглашению, по сумме заказа (порог), по количеству, акция на группу позиций
  с датами. Порядок применения и запрет суммирования — настройка; итоговая скидка видна в строке с расшифровкой «откуда».
- Пересчёт скидок только до подтверждения заказа; после — только явным действием с причиной.

## 4. Заказ покупателя: удобство и автоматизация
- Повтор заказа (А3 из `docs/automation.md`): «Создать по образцу» с актуальными ценами и проверкой остатков.
- Вставка строк из Excel/буфера (А4): артикул/штрихкод, размер, цвет, количество; ошибки — построчно, без потери введённого.
- Ввод по сетке «размер × цвет» для модели с модификациями (каталог).
- Значения по умолчанию (А5): склад, организация-продавец (юрлицо), договор, условия оплаты, менеджер — из соглашения и истории.
- Подбор позиций: поиск по артикулу, названию, штрихкоду; показ остатка (только через `WarehouseScope.VisibleMovements`),
  резерва, ожидаемого выпуска производства и цены.
- Дата отгрузки: обещанная клиенту и расчётная (остаток / производство); предупреждение при срыве.
- Частичная отгрузка и дозаказ: остаток неотгруженного виден в заказе и в журнале.
- Отмена с причиной (справочник), снятие резерва автоматически.

## 5. Кредитный контроль и дебиторка
- Перед подтверждением и перед отгрузкой: долг клиента + сумма заказа ≤ лимит договора/соглашения; просрочка по отсрочке
  `PaymentDays` → блок. Обход — право `sales.credit.override` с причиной и аудитом.
- Отчёт «Дебиторская задолженность» с разбивкой по срокам (не просрочено, 1–30, 31–60, 61–90, > 90 дней), по менеджерам.
- Акт сверки с покупателем (PDF), начальное сальдо из вводных остатков.
- Напоминания о просрочке менеджеру (в уведомлениях системы); письма клиенту — только шаблон для копирования (без рассылки
  из системы до решения владельца).

## 6. Отгрузка и логистика
- Задание на сборку для склада из заказа (список позиций по ячейкам/складу), отметка «собрано» двигает этап (D110).
- Отгрузка по нескольким заказам одного клиента; упаковочный лист, количество мест, вес.
- Способ доставки (самовывоз, своя доставка, транспортная компания) и номер отслеживания — справочником; без интеграций с ТК
  на этом этапе (только поля и печать).
- Возвраты от покупателя (есть `CreateReturnAsync`): причина возврата, качество (годен / брак → в карантин или списание),
  корректировочный УПД, возврат денег или зачёт в аванс.

## 7. Документы и ЭДО
- Проверить комплект печатных форм: счёт, УПД (статус 1 и 2), счёт-фактура, ТОРГ-12, ТТН по требованию, акт сверки,
  корректировочный УПД. Реквизиты — из юрлица продавца, подписанты — из настроек организации.
- Выгрузка УПД в формате ФНС (XML, приказ ФНС действующей редакции) для ручной загрузки в оператор ЭДО; прямая интеграция
  с операторами (Диадок, СБИС) — только проектом решения (D11xx), без кода, пока владелец не выберет оператора.
- Маркировка: коды маркировки в строках отгрузки для маркируемых позиций (сканирование), проверка, что код не продан дважды;
  выгрузка для вывода из оборота/передачи по ЭДО. Работа с API «Честного ЗНАКа» — отдельным решением.

## 8. Маркетплейсы (подготовка)
- Заказы и отгрузки FBS/FBO как отдельный канал продаж (справочник каналов), отчёты по каналам.
- Загрузка отчёта о реализации Wildberries/Ozon из файла (Excel) → продажи, возвраты, комиссии; сопоставление по внешним
  связям каталога. API маркетплейсов — без ключей в репозитории; ключи только в настройках организации, зашифрованно,
  и только после отдельного решения.

## 9. Аналитика продаж
- Отчёты: выручка и маржа по клиентам, менеджерам, группам, каналам, периодам; ABC-анализ клиентов и позиций;
  план-факт по менеджерам (план — ввод на месяц); средний чек, повторные покупки; воронка «заказ → отгрузка → оплата».
- Себестоимость и маржа — только при праве `finance.price.view`; без права — колонки скрыты и на сервере не отдаются.
- Блоки главного экрана: «Отгрузить сегодня», «Просроченная дебиторка», «Продажи за месяц к плану».
- Выгрузка любого отчёта в Excel; построение по большим периодам — не дольше 3 секунд на 100 тыс. строк (индексы).

## 10. Права и роли
- Новые права (префикс `sales.`, попадут в группу редактора ролей сами — D112): `sales.price.override`, `sales.credit.override`,
  `sales.agreement.edit`, `sales.discount.edit`, `sales.report.view`, `sales.plan.edit`, `sales.marking.edit`.
- Видимость заказов: свои / своего отдела / все — настройка роли (как в CRM); менеджер не видит чужие заказы без права.
- Дописать права в `Permissions.Labels` и `RoleMatrixP0` для `SalesManager`, `SalesHead`, Бухгалтера, Кладовщика, Владельца.

## 11. Обязательные правила (из базы)
- Каждое действие — `IAccessGuard.DemandAsync` на сервере; чужая организация → 404.
- Составные внешние ключи `(OrganizationId, Id)` на все таблицы организации; CHECK и UNIQUE в SQL Server.
- Документы не удаляются, исправление — новым документом; `rowversion` и конфликт пользователю; деньги `decimal(19,4)`.
- Миграции создавать только после слияния свежей базы; CHECK тегов/обсуждений (1…99) не трогать.
- Остатки вне складских экранов — только `WarehouseScope.VisibleMovements`.
- Переводы: `translations.py add` для каждой новой строки (ru, en, be, kk, uz); `TranslationCoverageTests` зелёный.
- Без паролей, ключей и реальных персональных данных в репозитории и тестах.
- Границы: CRM владеет сделками и лидами (`SalesOrder.CrmDealId`, `ISalesOrderEvents` — не ломать); каталог — ценами и
  маркировкой как справочниками; производство — `NotifyProductionAsync`; деньги — выпиской банка (D119).
  Изменения в чужих файлах — минимальные, с записью в `docs/sessions/sales.md` для сессии № 1.

## 12. Этапы и приёмка
| Этап | Содержание | Приёмка |
|---|---|---|
| 1 | Карта «есть/нет», соглашения, автоподстановка цены, мин. цена и обход с правом | Интеграционные тесты цены и обхода |
| 2 | Кредитный контроль, дебиторка по срокам, акт сверки | Тест блока отгрузки при лимите и просрочке |
| 3 | Повтор заказа, вставка из Excel, сетка размер × цвет, значения по умолчанию | e2e на телефоне 390 px |
| 4 | Скидки и акции с расшифровкой | Тесты порядка применения |
| 5 | Сборка, отгрузка по нескольким заказам, возвраты с качеством, корректировочный УПД | Тесты остатков и документов |
| 6 | Печатные формы, XML УПД, коды маркировки в отгрузке | Проверка XML по схеме ФНС |
| 7 | Аналитика, план-факт, блоки главного | Тест: без права цены — нет маржи в ответе сервера |
| 8 | Каналы и загрузка отчётов маркетплейсов из файла | Тест сопоставления по внешним связям |

Каждый этап: сценарий → миграция → сервис → права → форма → аудит → тесты (модульные, интеграционные с SQL, e2e Playwright,
телефон без горизонтальной прокрутки, 0 ошибок JS) → `has-pending-model-changes` пустой → запись в `docs/decisions.md` → пуш.
Отчёт владельцу после этапа: что сделано и проверено, что не проверено (явно), «Следующие 3 шага», «Готовность».
Слияние в базу делает сессия № 1.
