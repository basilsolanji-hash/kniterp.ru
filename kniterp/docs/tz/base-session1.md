# ТЗ сессии № 1 — база knitERP (разработка общего ядра)

Версия 1.0 от 13.10.2026. Составил GENERAL — координатор проекта (слияние модулей в базу, безопасность, ТЗ сессий; ветка
`claude/fervent-volta-3pn88r`). Заказчик — владелец продукта. Порядок прежний: сначала пилот на собственной фабрике, затем продажа
по подписке.

## 1. Роль и границы
- Сессия № 1 разрабатывает **общее ядро**: склад, закупки, деньги, расчёты, права, главная, API, автоматизация, сервер и выпуск.
- Ветка — **`claude/base-dev`** от свежей базы; в базу (`claude/fervent-volta-3pn88r`) **не пушить**: сливает и проверяет GENERAL,
  база сразу обновляет рабочий сервер фабрики.
  ```
  git fetch origin claude/fervent-volta-3pn88r
  git checkout -B claude/base-dev origin/claude/fervent-volta-3pn88r
  ```
  Перед каждым этапом: `git fetch origin && git merge origin/claude/fervent-volta-3pn88r`.
- Номера решений — **D140–D199** (D86–D139 заняты, D134–D139 — за GENERAL). Чужие диапазоны: D200–D299 «Сотрудники», D300–D399
  каталог, D400–D499 производство, D500–D599 контрагенты, D600–D699 CRM, D700–D799 «Разработка», D800–D899 интерфейс,
  D900–D999 база знаний, D1000–D1099 подписка, D1100–D1199 продажи (сессия закрыта — её хвосты здесь).
- **Не трогать:** `MainLayout.razor`, меню, верхнюю панель, блок пользователя, общие стили и `Shared/*` — их переделывает сессия
  интерфейса (ТЗ `docs/tz/ui-review.md`). Нужна точка встраивания — запишите просьбу в `docs/sessions/base.md`, раздел «Вопросы к базе».

## 2. Обязательные правила (кратко; полностью — `CLAUDE.md`, `docs/sessions/base.md`)
1. Каждое действие проверяет право на сервере (`IAccessGuard.DemandAsync`); чужая организация → 404; нельзя выдать право шире своего
   (D128); опасные админ-действия — повторное подтверждение (D123).
2. Учёт: документы не удаляются, исправление — новым документом; повтор нажатия не создаёт дублей (блокировка под транзакцией);
   конфликт версий возвращается пользователю; закрытый период запрещает изменения (D132).
3. Не ослаблять аудит 12–13.10: D121 (секрет MAX), D128, D129 (лимиты по заказу, Idempotency-Key), D130 (`tag.manage`, ПДн),
   D118 (остатки только через `WarehouseScope.VisibleMovements`), страница стартует после всех запросов меню.
4. Миграции — только новые и обратимые, после свежей базы; `has-pending-model-changes` — пусто.
5. Никаких паролей, ключей, реальных персональных данных и реальных ИНН в коде и тестах.
6. Переводы be/kk/uz: MISSING 0, STALE 0.
7. Перед сдачей этапа: модульные, интеграционные (SQL), сквозные .NET Playwright (1440 и 390 px, 0 ошибок JS). Скиллы:
   `kniterp-stage`, `kniterp-tests`, `kniterp-e2e`, `kniterp-translations`.
8. Отчёт — строго по-русски: сделано и проверено; не проверено (явно); «Следующие 3 шага»; «Готовность проекта» без процентов
   без расчёта.

## 3. Этапы (по порядку важности для пилота)

### Этап 1 — хвосты продаж и расчётов (D140–D144)
1. Зачёт переплаты в аванс после возврата (продажи D1154) меняет разноски в обход общего разносчика — добавить проверку закрытого
   периода (`period.closed`, как D133).
2. Главная: «Нам должны покупатели» учитывает вводные остатки покупателей (D1146), как «Мы должны поставщикам» учитывает D133.
   Не превышать лимит запросов главной (тест на 30 запросов).
3. Минимальная цена: подсветка строки (каталог D350) и проверка подтверждения (продажи D1104) сравнивают в разной величине (без НДС
   и с НДС). Одно правило — сравнивать в той величине, в которой задана минимальная цена; общий метод; тест на заказ без НДС и с НДС.
4. Акт сверки с поставщиком и с покупателем — проверить по шагам с вводными остатками, авансами, возвратами (сквозной e2e).

### Этап 2 — автоматизация, волна 2 (D145–D159)
1. **Курсы ЦБ РФ:** ежедневная загрузка (официальный XML ЦБ), справочник курсов, пересчёт валютных документов по курсу на дату;
   без сети — ручной ввод; фоновая служба с отключением настройкой.
2. **Регулярные операции:** шаблон денежной операции/документа с расписанием (аренда, связь, зарплатные авансы) — черновик
   создаётся по расписанию, проводит человек; журнал и отключение.
3. **Напоминания об оплате:** покупателю — за N дней до срока и при просрочке (письмо из шаблона, через очередь писем продаж),
   ответственному — в колокольчик; настройка организации, отписка; без ПДн в журналах.
4. **Автозакрытие:** заказ покупателя/поставщику, полностью отгруженный (поступивший) и оплаченный, закрывается сам (статус, журнал);
   ничего не закрывается при открытых возвратах.
5. **УПД поставщика из XML** (формат 5.03): загрузка файла → черновик поступления по заказу поставщику с сопоставлением позиций
   (артикул, штрихкод, внешние связи каталога), несопоставленные — списком «привязать»; проверка ИНН продавца и покупателя;
   файл и разбор — с ограничением размера и без внешних сущностей XML (XXE).

### Этап 3 — выпуск и сервер (D160–D169)
1. **Быстрое обновление сервера:** сейчас `update.sh` собирает образ на сервере 10–25 минут. Сделать сборку образа в GitHub Actions
   с публикацией в реестр (GHCR) по каждому коммиту базы, тег = коммит; `update.sh` скачивает готовый образ (1–2 мин), при
   недоступности реестра — прежняя локальная сборка. Секреты — только в настройках GitHub и сервера, не в репозитории; образ без
   секретов. Проверить, что репозиторий приватный (иначе образ публичный — согласовать с GENERAL).
2. Проверка `update.sh` и `restore.sh` на чистой машине (Docker в тестовой среде): копия → обновление → откат.
3. Подкачка (swap) и проверка памяти в `install.sh`/чек-листе, если на сервере < 4 ГБ ОЗУ.

### Этап 4 — пилот (D170–D179)
1. Памятки по ролям из `docs/pilot.md` раздел 5 — печатные PDF по одной странице на роль (кладовщик, менеджер, начальник цеха,
   работник цеха, кадровик, бухгалтер, администратор).
2. Сценарий первого дня: мастер «Готовность к запуску» проверяет почту (тестовое письмо), копии, отпечатки копий, пользователей с 2FA.
3. Сверка XML УПД со схемой ФНС `ON_NSCHFDOPPR_1_997_01_05_03_01.xsd` — как только владелец пришлёт файл: схема в тестовые ресурсы,
   автоматическая проверка выгрузки (продажи) и загрузки (этап 2.5).

### Этап 5 — стабильность (D180–D189)
1. Нестабильные сквозные тесты (`AssistantKbE2ETests.*` и др.): причина, а не повтор; 3 полных прогона подряд зелёные.
2. Журнал приложения e2e (`kniterp-e2e-app-*.log`) — проверка, что в нём нет «second operation on this context» и необработанных
   исключений, автоматическим тестом после прогона.

## 4. Сдача
Каждый этап — отдельным набором коммитов в `claude/base-dev` с пушем и отчётом владельцу; владелец пишет GENERAL «Сливай модули».
Приёмка этапа — у GENERAL: сборка, модель, переводы, 3 вида тестов, проверка безопасности по разделу 2.
