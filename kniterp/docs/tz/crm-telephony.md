# ТЗ: IP-телефония с записями разговоров в CRM — проект решения

Версия 0.1 от 13.10.2026, сессия CRM (`claude/crm`). Статус: **проект для решения владельца**, кода нет. Продолжение
`docs/tz/crm.md` §7 («Почта и телефония — следующий этап, после решения владельца») и `docs/tz/crm-automation.md` §5.
Опирается на D640–D644 (приём звонков через API), D670–D679 (вебхуки мессенджеров, шифрование, удаление ПДн).
Номера решений для реализации — из свободных в D685–D698, присваиваются при сдаче этапа.

Все цены, сроки хранения и детали API провайдеров в этом документе — **ориентиры, их нужно уточнить у провайдера на дату
выбора** (тарифы и документация меняются). Там, где данных нет, стоит «уточнить».

## 1. Цель и сценарии

Цель: менеджер не записывает звонки руками и не теряет клиентов. Каждый разговор с клиентом попадает в ленту лида, сделки
или контакта сам; руководитель может прослушать разговор и видит пропущенные звонки.

Что уже есть: `POST /api/v1/crm/calls` (D643) → `CrmIntakeService.RegisterCallAsync(CrmCallEvent)`: номер → контакт (и его
открытая сделка) или открытый лид; незнакомый номер — новый лид с источником «Звонок»; активность `Call` с
`Source = Telephony`, повтор по `ExternalRef` (id звонка АТС) не задваивается; длительность 0 — «не дозвонились». Нет: приёма
событий прямо от АТС (нужен посредник, который вызовет API), всплывающей карточки, звонка по клику, записей, пропущенных-задач,
сопоставления внутреннего номера с пользователем.

| № | Сценарий | Что видит пользователь | Как работает |
|---|---|---|---|
| Т1 | **Входящий звонок → карточка (screen pop)** | В открытой вкладке knitERP у менеджера, на чей внутренний номер идёт вызов, — всплывающее окно: «Звонит: Иван (ООО «Пример»), сделка С-00012 — открыть» или «Неизвестный номер +7 900 ***-**-01 — создать лид» | Событие АТС «вызов на внутренний номер» → поиск по номеру (как в `RegisterCallAsync`, без записи) → уведомление в открытую вкладку пользователя |
| Т2 | **Исходящий по клику (click-to-call)** | Кнопка «Позвонить» рядом с телефоном в карточках лида, сделки, контакта и в «Моих задачах CRM» | Команда АТС «обратный вызов»: сначала звонит телефон/софтфон менеджера, после ответа — клиенту; звонок затем приходит событием как обычный исходящий |
| Т3 | **Звонок в ленту** | Активность «Входящий/Исходящий звонок»: кто (менеджер), с кем, когда, длительность разговора, результат (разговор, пропущен, занято, не дозвонились) | Событие АТС «звонок завершён» → расширенный `RegisterCallAsync` |
| Т4 | **Запись разговора** | В активности звонка — плеер «Прослушать» (для тех, у кого есть право), длительность, срок хранения | Фоновая очередь скачивает запись у АТС в своё хранилище; прослушивание — через сервер с проверкой прав и записью в журнал |
| Т5 | **Пропущенный → «Перезвонить»** | Задача «Перезвонить: +7 900 ***-**-01» ответственному, срок — через N минут (по умолчанию 15), колокольчик | Входящий без ответа (или ответ короче порога) → задача; если клиент дозвонился сам или менеджер перезвонил — задача закрывается автоматически с пометкой |
| Т6 | **Неизвестный номер → лид** | Новый лид «Звонок +7 …», источник «Звонок», ответственный — кто ответил, иначе по правилу распределения | Уже есть в `RegisterCallAsync`; добавить: если ответил конкретный менеджер — он и ответственный |
| Т7 | **Распределение входящих** | Звонок известного клиента попадает сначала его ответственному менеджеру, при неответе — в общую группу | У АТС с запросом маршрута во внешнюю систему — knitERP отвечает внутренним номером ответственного; иначе — группа АТС и screen pop всем, кому звонит |

Негативные случаи: звонок с внутреннего на внутренний (не в CRM); скрытый номер (лид не создаётся, только запись в журнал
звонков); номер, удалённый по запросу (D613), — новый лид не создаётся без нового обращения; повтор вебхука; события пришли не по
порядку (завершение раньше начала); звонок длиннее суток (уже отклоняется, `MaxCallSeconds`); менеджер без внутреннего номера.

## 3. Архитектура в knitERP

### 3.1. Слои
| Слой | Что добавляется |
|---|---|
| Domain/Crm | `CrmTelephonyChannel`, `CrmTelephonyExtension`, `CrmCall`, `CrmCallRecording`, `CrmCallListenLog`; перечисления: провайдер, направление, итог звонка, состояние записи |
| Application/Crm | Интерфейс `ICrmTelephonyProvider`, сервисы `CrmTelephonyService` (настройки, click-to-call, обработка событий), `CrmCallRecordingService` (прослушивание, сроки, удаление); общий разбор события `CrmTelephonyEvent`; расширение `CrmIntakeService.RegisterCallAsync` |
| Infrastructure | Адаптеры `MangoTelephonyProvider`, …, `GenericTelephonyProvider` (свой формат), `FakeTelephonyProvider` (только Development и тесты); хранилище записей `IRecordingStore` (диск сервера, шифрование) |
| Web | Вебхук `/hooks/crm/telephony/{provider}/{secret}`, отдача записи `/crm/calls/{id}/recording`, фоновая `CrmRecordingWorker`, панель «Телефония» в настройках CRM, всплывающее окно звонка в `MainLayout` |

### 3.2. Интерфейс адаптера (эскиз)
```csharp
public interface ICrmTelephonyProvider
{
    CrmTelephonyProviderKind Kind { get; }
    // Подлинность: подпись/заголовок/токен провайдера; сравнение за постоянное время. Секрет в адресе проверен до вызова.
    bool Authentic(Func<string, string?> header, byte[] body, CrmTelephonyCredentials credentials);
    // Разбор тела в общие события (одно тело может нести несколько событий); неизвестные события — пустой список.
    IReadOnlyList<CrmTelephonyEvent> Parse(byte[] body, string contentType);
    Task<CrmClickToCallResult> StartCallAsync(CrmTelephonyCredentials c, string extension, string phoneE164, CancellationToken ct);
    Task<Stream> OpenRecordingAsync(CrmTelephonyCredentials c, string recordingRef, CancellationToken ct);
    Task<CrmTelephonyCheck> CheckAsync(CrmTelephonyCredentials c, CancellationToken ct);                 // кнопка «Проверить»
    Task<IReadOnlyList<CrmTelephonyCallSummary>> HistoryAsync(CrmTelephonyCredentials c, DateTime fromUtc, CancellationToken ct); // сверка
}
```
`CrmTelephonyEvent`: вид (вызов начат, звонит на внутренний номер, ответ, завершён, запись готова), id звонка АТС, id события,
направление, внешний номер, внутренний номер, время по UTC, длительность разговора, итог, ссылка/идентификатор записи.
Адреса API провайдеров — только из настроек сервера `Telephony:{Провайдер}:BaseUrl` (как `Messengers:*`, D670), не из ввода
пользователя — нет SSRF. `HttpClient` адаптеров — без журнала запросов (D678), таймаут 10 с.

### 3.3. Вебхук
`POST /hooks/crm/telephony/{provider}/{secret}` — без входа, по образцу `/hooks/crm/{messenger}/{secret}` (D673):
1. Провайдер известен, иначе 404. `Content-Length` > 64 КБ — 413; тело читается `ReadBodyAsync` с тем же пределом.
2. Канал организации — по провайдеру и SHA-256 секрета из адреса (секрет хранится только хэшем); не найден или выключен — 404.
3. Подлинность — подписью провайдера (`Authentic`), ключи — расшифровкой мастер-ключом (`KeyRing`, AES-256-GCM);
   сравнение — `CryptographicOperations.FixedTimeEquals`. Неверно — 404, в базу ничего не пишется. Если провайдер публикует
   список IP — дополнительная проверка (настройка, по умолчанию выключена).
4. Лимит — существующий для `/hooks` (120 за 10 с с IP); проверить на пиковой нагрузке АТС, при необходимости — отдельная ветка
   лимита для `/hooks/crm/telephony` с ключом «провайдер + IP».
5. Обработка — быстро (провайдер ждёт ответ 1–3 с, иначе повторяет): событие пишется в `crm_telephony_events` (дедупликация по
   id события), screen pop отправляется сразу, тяжёлое (лента, лид, задача) — в той же транзакции, но без внешних вызовов;
   скачивание записи — только постановкой в очередь. Ответ 200 даже на неизвестный вид события (чтобы не было повторов).
6. Действия выполняются **с правами подключившего канал** (как D648/D676): если у него отозваны `crm.edit`/`crm.settings` —
   события не обрабатываются, в колокольчике Владельца — «Телефония отключена: у подключившего нет прав».

Запрос маршрута (Т7), если провайдер его поддерживает: `POST /hooks/crm/telephony/{provider}/{secret}/route` → внутренний номер
ответственного за найденного клиента; ответ за ≤ 500 мс из одного индексированного запроса, при ошибке — пустой ответ (АТС ведёт
по своему сценарию).

### 3.4. Связь с `RegisterCallAsync`
- Выделить ядро `RegisterCallCoreAsync(db, organizationId, actorUserId, CrmCallEvent, ct)`: API v1 вызывает его с пользователем
  токена, вебхук — с подключившим. Публичный контракт `POST /api/v1/crm/calls` не меняется.
- `CrmCallEvent` дополняется необязательными полями в конце (обратно совместимо): `StartedAtUtc`, `TalkSeconds`, `Status`
  (answered / missed / busy / failed), `Extension`, `RecordingRef`. Пользователь — по `Extension` через `crm_telephony_extensions`.
- Звонок пишется в `crm_calls` (одна строка на id звонка АТС, UNIQUE `(OrganizationId, ChannelId, ExternalCallId)`), активность —
  как сейчас (`ExternalRef` = id звонка), `crm_calls.ActivityId` → активность. Повторное «завершён» обновляет звонок, а не
  создаёт активность.
- Пропущенный входящий → задача «Перезвонить» (`CrmActivitySource.Telephony`); исходящий или входящий отвеченный звонок по тому же
  номеру позже → задача закрывается с результатом «перезвонили {время}».
- Если ответил менеджер, а объект чужой (ответственный другой) — активность в ленту объекта, исполнитель — ответивший; видимость
  записи — по правилам объекта (§4).

### 3.5. Записи разговоров — хранение
Объём: в зависимости от формата провайдера (MP3 моно 32–128 кбит/с) — порядка **0,25–1 МБ на минуту**. Пример: 10 менеджеров ×
30 разговоров × 3 мин × 22 дня ≈ 20 000 мин/мес ≈ 5–20 ГБ в месяц. Поэтому **не в `varbinary` базы**, как `ItemPhoto` (2 МБ) и
`CounterpartyContractFile` (5 МБ): база и резервные копии вырастут в разы.

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Только ссылка у провайдера | Ноль места, быстро сделать | Срок хранения и доступность — у провайдера; ссылка часто временная или требует ключа; при смене провайдера записи теряются; журнал прослушиваний неполный |
| **Б. Своё хранилище на диске сервера (рекомендуется)** | Свой срок хранения и удаление, единый журнал, не зависим от провайдера, данные там же, где база (РФ) | Место на диске и его резервное копирование; нужно шифрование |
| В. S3-совместимое хранилище в РФ (Yandex Object Storage, Selectel и др.) | Масштаб, дешёвое хранение | Ещё один поставщик-обработчик ПДн (договор поручения), ещё одни ключи; позже, если диска мало |

Правила для Б: файл `{организация}/{год}/{месяц}/{guid}.bin` в каталоге `Telephony:RecordingsPath` вне wwwroot; шифрование
AES-256-GCM ключом, выведенным из мастер-ключа (`KeyRing`), с отпечатком ключа в записи (смена ключа — перешифровка фоном);
SHA-256 и размер — в базе; файл отдаётся только через `/crm/calls/{id}/recording` (проверка прав, поддержка Range для перемотки,
`Cache-Control: no-store`). Предел файла — 200 МБ (настройка).

Очередь загрузки (`CrmRecordingWorker`, раз в 30 с, по 20 записей): состояния `Pending → Downloading → Stored | Failed`;
попытки с паузой 1, 5, 15, 60 мин, до 10 попыток, затем `Failed` и уведомление подключившему; после сохранения — запрос на удаление
у провайдера (настройка, если API позволяет — уточнить). Сверка: раз в 15 мин `HistoryAsync` за последние 2 часа — звонки, чей
вебхук потерялся, дописываются.

Удаление по сроку: ежедневно файлы с `ExpiresAtUtc` в прошлом удаляются, строка записи остаётся с `ErasedAtUtc` и причиной
(«срок хранения»). Метаданные звонка (кто, когда, длительность) живут как активность ленты.

### 3.6. Screen pop в Blazor
- Сейчас колокольчик `MainLayout` обновляется раз в минуту — для звонка мало. Нужен мгновенный путь: синглтон
  `CrmCallSignals` (в памяти процесса) — событие «пользователю X звонит Y» с готовыми данными (имя, компания, номер маской,
  ссылка на карточку). Обработчик вебхука после поиска клиента публикует сигнал; `MainLayout` подписан на сигналы своего пользователя
  и показывает плашку через `InvokeAsync(StateHasChanged)` — **без запроса к базе** в обработчике, поэтому правило «один DbContext
  на вкладку, без параллельных вызовов» не нарушается.
- Плашка: «Входящий: Иван, ООО «Пример» · сделка С-00012 [Открыть] [Скрыть]», для незнакомого — «[Создать лид]» (форма лида
  с подставленным номером). Исчезает по «ответ на другом номере»/«завершён». Телефон 390 px — плашка сверху на всю ширину.
- Несколько вкладок одного пользователя — плашка во всех. Пользователь без `crm.view` плашку не получает.
- Ограничение: сигнал в памяти одного процесса. Для пилота (один сервер) достаточно; при нескольких экземплярах — общий канал
  (SQL-опрос раз в 2 с или Redis) — отдельное решение.
- Звонок, на который пользователь не ответил, — в колокольчик («Пропущенный звонок …») и задача (Т5).

### 3.7. Click-to-call
`CrmTelephonyService.CallAsync(target, targetId, phone)`: право `crm.calls.make` + объект виден пользователю (иначе 404); у
пользователя есть внутренний номер; номер — E.164; лимит 20 вызовов в минуту на пользователя; аудит «звонок по клику» с маской номера.
Вызов `StartCallAsync` у провайдера; ответ «Ваш телефон сейчас зазвонит». Связь звонка с объектом: id звонка из ответа провайдера
(если отдаёт) → `crm_calls.TargetHint`, чтобы активность легла именно в эту сделку, а не в последнюю открытую по номеру.

## 4. Персональные данные и закон

| Тема | Требование | Как в knitERP |
|---|---|---|
| Уведомление собеседника | Перед записью клиент должен быть предупреждён («разговор записывается в целях качества обслуживания») | Голосовое приветствие на входящих — настройка АТС; на исходящих — автоматическое сообщение АТС (если поддерживается) или скрипт менеджера. В панели «Телефония» — флажок «Предупреждение о записи включено в АТС» обязателен для включения записи |
| Основание обработки (152-ФЗ ст. 6) | Для клиентов — исполнение/заключение договора или законный интерес оператора; при сомнении — согласие | Используется основание контакта (D611); в политике обработки ПДн организации — пункт о записи звонков (цель, срок, состав) |
| Голос — биометрия? | Запись голоса без цели установления личности по голосу биометрией не считается (позиция РКН — проверить актуальность) | knitERP не использует голос для идентификации; расшифровка речи — отдельное решение (§7) |
| Сотрудники | Работодатель уведомляет сотрудников о записи рабочих звонков (локальный акт, ознакомление под подпись) | Вне knitERP; в панели — напоминание |
| Срок хранения | Не дольше, чем требует цель (ст. 5 ч. 7) | Срок задаёт организация: по умолчанию 90 дней (вопрос владельцу), диапазон 7–1095 дней; удаление по сроку автоматически |
| Доступ | Только тем, кому нужно по работе | Права `crm.calls.listen` / `crm.calls.listen.all` / `crm.calls.download` (§5), видимость по объекту |
| Журнал прослушиваний | Подтверждение, кто и когда получал доступ | `crm_call_listen_log` — только вставка (триггер, как журнал аудита): кто, когда, запись, действие (прослушал/скачал), IP маской |
| Удаление по запросу (ст. 14, 21) | Удалить ПДн субъекта | Развитие D613/D677: при удалении контакта — файлы записей его звонков стираются, номер в `crm_calls` заменяется маской, событие АТС — без номера; запрос на удаление у провайдера (если API позволяет, иначе — инструкция для ручного удаления в кабинете) |
| Локализация (ст. 18 ч. 5) | Сбор и хранение ПДн граждан РФ — в базах на территории РФ | Провайдер с хранением в РФ, своё хранилище — на сервере в РФ |
| Обработчик | Провайдер АТС и сервис расшифровки — обработчики по поручению (ст. 6 ч. 3) | Договор с провайдером с условием поручения; иностранный сервис — трансграничная передача, уведомление РКН |
| Тайна связи | Записывает абонент (организация) как участник разговора через свою АТС | Записи только звонков организации; внутренние звонки сотрудников между собой — не в CRM |
| Маскирование | Номера в аудите и журналах — маской (D612) | Так же для `crm_telephony_events` и журналов вебхука |
| РУз, РК, РБ | Свои законы о ПДн: требования к локализации (РК, РУз), трансграничной передаче и записи разговоров | **Нужна проверка местным юристом до запуска** в каждой стране; до неё — запись по умолчанию выключена |

| Риск | Мера |

### 6.2. Критерии приёмки
1. Входящий от известного клиента → плашка у менеджера ≤ 2 с после события АТС (1440 и 390 px), ссылка ведёт в карточку.
2. Завершённый звонок → активность в ленте нужного объекта с длительностью и итогом; повтор вебхука — без дубля.
3. Пропущенный → задача «Перезвонить» ≤ 1 мин; после перезвона — закрыта автоматически.
4. Неизвестный номер → лид с источником «Звонок»; ответственный — ответивший или по правилу распределения.
5. Click-to-call: звонок по кнопке, активность в той же сделке.
6. Запись доступна ≤ 10 мин после звонка; без права — нет плеера, прямой адрес → 404/403; каждое прослушивание — в журнале.
7. Неверная подпись/секрет → 404, в базе ничего не появилось; тело > 64 КБ → 413.
8. Запись старше срока удалена ≤ 24 ч; удаление ПДн контакта стирает его записи и номера в звонках.
9. Чужая организация → 404 везде; ключи в базе зашифрованы, в журналах номера маской.

## 7. Вопросы владельцу

1. **Провайдер.** Есть ли у фабрики оператор/АТС сейчас (номера, договор)? Перенос номера возможен, но займёт время. Выбор из §2 или
   рекомендация §8.
2. **Бюджет** в месяц на телефонию (пользователи × абонплата + минуты + хранение) и число менеджеров на пилоте.
3. **Запись разговоров**: включать на пилоте? Срок хранения — 30, 90 (предложение) или 180 дней?
4. **Кто слушает**: менеджер — свои звонки; руководитель продаж и Владелец — все? Нужно ли скачивание файлов кому-либо, кроме Владельца?
5. **Распределение**: звонок известного клиента — сразу ответственному (с переходом в группу через N секунд) или в общую очередь?
6. **Пропущенные**: через сколько минут ставить «Перезвонить» и кому — ответственному клиента или дежурному?
7. **Расшифровка речи в текст** нужна? Если да — внешний сервис (SpeechKit Yandex, сервис провайдера АТС — данные в РФ, договор
   поручения, оплата за минуты) или локально (открытые модели Whisper/Vosk на своём сервере — нужен GPU или медленно, зато данные не
   покидают сервер)? И нужны ли сводки разговоров помощником (D116)?
8. **Страны**: когда нужна телефония в РК/РУз/РБ — для них заранее запросить местного юриста и операторов (§2.2).
9. Хранить записи **у себя** (рекомендация) или только ссылкой у провайдера?

## 8. Рекомендация для пилота в России

**Манго Офис + своё хранилище записей + «общий» адаптер в архитектуре.**

Почему Манго Офис:
- зрелый API ВАТС: подписанные вебхуки событий звонка и готовности записи, обратный вызов, скачивание записей — всё, что нужно для
  Т1–Т5, без своей АТС;
- готовая офисная АТС «из коробки»: группы, очереди, голосовое меню, приветствие «разговор записывается», мобильное приложение для
  менеджеров вне офиса;
- данные в РФ, широко используется в интеграциях с CRM — меньше неожиданностей в документации и поддержке.

Оговорки:
- цены — не самые низкие; если бюджет главный, альтернатива — **Sipuni** или **Novofon** (проще и дешевле, API достаточный —
