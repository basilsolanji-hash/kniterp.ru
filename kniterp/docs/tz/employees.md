# ТЗ: модуль «Сотрудники» (кадры, табель, сдельная оплата) — для отдельной сессии Claude

Версия 1.0 от 11.10.2026. Исполнитель — третья сессия Claude. Параллельно работают:
сессия № 1 (склад, деньги, продажи, API, теги — ветка `claude/fervent-volta-3pn88r`) и сессия № 2 (производство).

## 0. Правила совместной работы (обязательно)
1. Своя ветка от актуальной `claude/fervent-volta-3pn88r`, например `claude/hr-employees`. В чужие ветки не пушить, чужие ветки не сливать без просьбы владельца.
2. Номера решений в `docs/decisions.md` — **только D200–D299** (D86–D109 и D110–D199 — сессия № 1, D90–D99 — производство).
3. Не трогать производство: `Domain/Production`, `Application/Production`, страницы техкарт и производственных заказов, НЗП, выдачу пряжи в производство, выпуск. Данные выработки получать только через интерфейс из п. 6.
4. Не менять чужие таблицы и миграции. Свои миграции — с префиксом `Hr…` (`dotnet ef migrations add HrTimesheets -p src/KnitErp.Infrastructure -o Persistence/Migrations`). Применённые миграции не редактируются. Триггеры — текстом `EXEC(N'...')`.
5. Соблюдать `CLAUDE.md`: права на сервере через `IAccessGuard`, организация из сессии (чужое → 404), `rowversion`, журнал аудита, один DbContext на вкладку Blazor, допущения как Dxx.
6. Никаких реальных персональных данных в коде и тестах (152-ФЗ); вымышленные ФИО, СНИЛС/ИНН — только тестовые с верной контрольной суммой.
7. Каждый шаг: реализация → модульные + интеграционные тесты (SQL Server) + e2e Playwright → коммит → пуш → отчёт по-русски с «Готовность проекта» и «Следующие 3 шага». Переводы интерфейса be/kk/uz — тест `TranslationCoverageTests` должен проходить.

## 1. Что уже есть (не ломать)
- `Domain/Structure/Employee.cs`: табельный номер, ФИО, подразделение, должность, статус (Работает / Отпуск / Уволен), даты приёма/увольнения, день рождения, связь с учётной записью.
- `StructureService`, `EmployeeService`, `EmployeeExchangeService` (импорт/экспорт Excel), страницы `EmployeesPage`, `StructurePage`.
- Права `hr.employee.view`, `hr.employee.edit`, `hr.personal_data.view` (персональные данные — отдельное право, не выдаётся через API).
- Подотчётные лица и авансовые отчёты (`AccountableService`) ссылаются на сотрудника — не менять их контракт.

## 2. Этап 1 — личная карточка и персональные данные (Т-2)
- Отдельная таблица персональных данных (паспорт, СНИЛС, ИНН, адрес регистрации, телефон, образование, семейное положение), доступ — только с правом `hr.personal_data.view`/нового `hr.personal_data.edit`; хранение — шифрованием (`SecretCipher`, как в интеграциях); каждое чтение — запись в журнал аудита (кто смотрел).
- Согласие на обработку ПДн (ст. 9 152-ФЗ): дата, срок, файл скана; без согласия — предупреждение.
- Проверки: СНИЛС (контрольная сумма), ИНН физлица (12 цифр, контрольные), дата рождения ≥ 14 лет к дате приёма.
- Печать личной карточки по форме Т-2 (постановление Госкомстата № 1 от 05.01.2004).

## 3. Этап 2 — кадровые приказы
- Приём (Т-1), перевод (Т-5), отпуск (Т-6), увольнение (Т-8) с основаниями по ТК РФ (ст. 77, 80, 81 — справочник оснований с формулировкой и ссылкой на статью).
- Приказ — документ: черновик → проведён; проведённый не меняется, исправление — новым приказом (как складские документы). Проведение меняет статус/подразделение/должность сотрудника и пишет историю назначений (только вставка).
- Штатное расписание (Т-3): подразделение, должность, ставок, оклад; приём сверх штата — запрет.
- Печать форм Т-1, Т-5, Т-6, Т-8.

## 4. Этап 3 — учёт рабочего времени (табель Т-12/Т-13)
- Производственный календарь уже есть (`ProductionCalendar`) — использовать.
- Табель за месяц: коды явок/неявок по Т-12 (Я, Н, В, ОТ, Б, К, НН, ПР…), часы, автоматическое заполнение по графику, ручные правки с журналом.
- Графики работы: пятидневка, сменные (2/2, 3/3), длительность смены; суммированный учёт.
- Связь с рабочим днём из «Рабочего дня» (боковая панель, `WorkdayService`) — только чтение отметок.
- Закрытие табеля (как закрытый период склада): после закрытия — только исправительный табель.
- Печать Т-13, выгрузка в Excel.

## 5. Этап 4 — сдельная оплата вязальщиц (расчёт заработка, без бухгалтерии НДФЛ)
- Расценки: операция/изделие → цена за штуку или за кг; история расценок по датам.
- Начисление за месяц = Σ (выработка × расценка) + оклад/тариф × отработанное время + доплаты (ночные — ст. 154 ТК, сверхурочные — ст. 152 ТК, праздничные — ст. 153 ТК).
- Расчётный листок (ст. 136 ТК) — печать и личный кабинет сотрудника (видит только свой).
- Выгрузка начислений в 1С: «Зарплата и управление персоналом 3» через EnterpriseData — согласовать с сессией № 1 (сервис `EnterpriseDataExportService`, раздел добавить отдельным классом, не меняя существующий).
- НДФЛ, взносы, отчётность в СФР/ФНС — **вне объёма** (ведёт 1С ЗУП).

## 6. Граница с производством (согласовать с сессией № 2)
- Производство публикует выработку через интерфейс в `Application`:
  ```csharp
  public interface IWorkOutputSource
  {
      Task<IReadOnlyList<WorkOutputDto>> OutputAsync(long organizationId, DateOnly from, DateOnly to, CancellationToken ct);
  }
  public sealed record WorkOutputDto(long EmployeeId, DateOnly Date, long OperationId, string OperationName, long? ItemId, decimal Quantity, string Unit);
  ```
- Модуль «Сотрудники» объявляет интерфейс и заглушку (пустой список) в своей ветке; реализацию пишет сессия № 2 у себя. До слияния расчёт сдельщины тестируется на заглушке с тестовыми данными.

## 7. Права (добавить в матрицу ролей, D200+)
- `hr.order.create`, `hr.order.post` — кадровые приказы; `hr.timesheet.edit`, `hr.timesheet.close`; `hr.payroll.view`, `hr.payroll.calculate`; `hr.personal_data.edit`.
- Владелец — всё; Руководитель — просмотр и закрытие табеля; Кадровик (новая роль) — приказы, табель, ПДн; Мастер цеха — табель своего подразделения (область — подразделение, по аналогии с областью склада).
- Сотрудник со своей учётной записью видит только свой табель и расчётный листок.

## 8. Нефункциональные требования
- Деньги `decimal(19,4)`, часы `decimal(9,2)`, даты — `date`, время — UTC `datetime2(3)`.
- Журнал аудита на каждое изменение; документы не удаляются.
- Адаптивность: телефон 390 px без горизонтальной прокрутки; таблицы табеля — горизонтальная прокрутка внутри блока.
- Запросы главного экрана не утяжелять (тест: ≤ 30 запросов).

## 9. Порядок сдачи
Этап 1 → 2 → 3 → 4, каждый отдельным коммитом с решениями D2xx и тестами. После каждого этапа — краткий отчёт владельцу и готовность к слиянию (без самостоятельного слияния).
