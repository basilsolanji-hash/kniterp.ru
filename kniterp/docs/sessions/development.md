## Подсказки другим сессиям (12.10.2026)
- **Всем (Blazor):** если на странице несколько компонентов грузят данные независимо (вкладки, блоки), они делят DbContext вкладки —
  быстрые клики дают «A second operation was started» и обрыв сеанса. Решение — общая очередь (`DevGate` в Web) или короткий контекст
  `IKnitErpDbContextFactory`. Проверяйте сквозным тестом: щёлкнуть все вкладки подряд без ожидания.
- **Всем (файлы):** превью картинки не пишите в журнал аудита на каждое открытие — журнал засоряется; пишите скачивание.
  Минимальный параметр `bool?` в minimal API из `?x=1` даёт 400 — берите `string?`.
- **Всем (e2e):** сообщение статуса с тем же текстом остаётся на экране от прошлого действия — после клика ждите NetworkIdle и
  фильтруйте `GetByRole(Status).Filter(HasText)`. Скриншоты для владельца — отдельный тест по переменной окружения (`DevScreenshotTests`).
- **Производству:** техкарта вязания разработки открывается с `production.stage.mark` — вязальщицам не нужен доступ к моделям.
  Этап производства операции технолога — ваши коды 1–5 (D401). Для передачи в производство (этап 6) заправку, нормы и программу
  отдадим в черновик техкарты — сигнатуру метода предложим до начала этапа.
- **«Сотрудникам»:** операции технолога несут плановую расценку для себестоимости; сдельные расценки остаются вашими. Если
  захотите подтягивать норму времени операции из разработки в расценку — код операции = этап 1–5.
- **Каталогу:** палитра модели ссылается на позиции «Сырьё»/«Материалы» (составной FK). При слиянии позиций сообщите — перенесём ссылки.

- **Всем (вёрстка, 12.10):** правило `.panel form { flex-direction: column }` в `App.razor` перебивает `.inline-form` — форма в строку
  внутри `.panel` становится колонкой, прижатой вправо, и оставляет пустое поле. В модуле исправлено в `DevStyles` (от 600 px);
  базе предлагаю `.panel form.inline-form { flex-direction: row; align-items: flex-end }` в `App.razor` для всех модулей.
  Владелец просит экраны без пустых площадей: факты карточки — плитками (`dl > div`), панели — сеткой `auto-fit`, списки — плитками.
- **Всем (обсуждения):** объект модуля подключается к обсуждениям без правки `ObjectDirectory` — `ObjectDirectory.Register(TaggedEntity.X, describer)`
  в регистрации сервисов (пример — `DevObjects.Register()`); в интеграционном тесте вызвать регистрацию явно, хост не вызывает `AddApplication`.
- **Каталогу/складу:** для этикеток модуля переиспользован ваш `Barcode128`; общий конструктор этикеток (D316) — только для позиций.
  Если сделаете шаблоны этикеток для любых объектов — переведём этикетки разработки на них.

- **Производству (D750):** черновик техкарты из разработки создаётся вашими методами `TechCardService.CreateAsync`, `SetLineAsync`,
  `SetRouteAsync` внутри транзакции разработки (вложенная транзакция присоединяется). Комментарий техкарты начинается с «Из разработки:
  модель М-…». Если поменяете сигнатуры или добавите обязательные поля — сообщите. Отходы в нормах 0 % — задаёте вы.
- **Складу (D721):** разработка создаёт черновик «Списания» через `StockDocumentService.CreateWithLinesAsync` (комментарий «Пряжа на образец
  № N модели …»); проведение — ваше. Если появится причина списания «Образцы разработки» — подставим её по умолчанию.
- **Каталогу (D750):** при передаче создаётся позиция «Готовая продукция» через `CatalogService.CreateItemAsync` (описание «Из разработки:
  модель …»). Модификации (размер × колорит) не создаём, пока нет вашего метода «позиция с модификациями» — предложите сигнатуру.
- **Всем (одновременная правка таблиц, D720):** для таблиц, которые сохраняются целиком, — шлите только изменённые ячейки со значением,
  которое видел пользователь, и возвращайте конфликты по ячейкам (`DevCellEdit`/`DevSaveResult` в модуле разработки): никто не теряет
  правки, и не нужна блокировка всей таблицы.

- **Всем (слияние, 12.10):** если база уже влила вашу ветку, `git merge` пройдёт перемоткой — ваша миграция УЖЕ в базе. Перед пересозданием
  миграции проверьте `git merge-base --is-ancestor <ваш коммит> origin/<база>`: пересоздавать влитую миграцию нельзя — снимок базы
  может отставать, и новая миграция «создаст» чужие таблицы повторно.
- **«Сотрудникам» (D740):** работа в себестоимости = расценка операции технолога за штуку, иначе минуты × ставка из настроек разработки.
  Когда появится ваш сервис расценок — дайте метод «расценка операции/этапа на дату», подключим вместо ставки.
- **Закупкам (D740):** цена пряжи в расчёте — последняя строка подтверждённого или закрытого заказа поставщику, без НДС (как в планировании
  материалов производства). Если появится «средняя цена закупки» или цена поступления — сообщите.
- **Каталогу (D753):** при передаче используем `ModificationService.CharacteristicsAsync/CreateCharacteristicAsync/CreateModificationsAsync/AddPhotoAsync`
  внутри транзакции разработки; характеристики «Размер» и «Цвет» ищем по названию.

- **Базе (главный экран, D762, D723):** `IDevelopmentDashboardSource.GetAsync(db, ctx, today, ct)` → `DevDashboardData(InWork, Overdue, SamplesWaiting,
  Href, SamplesAtCustomer, SamplesOverdue)` (ТЗ §12: «образцы у заказчиков»), без `dev.view` — null; зарегистрирован в `AddApplication`.
  Подключите к блоку «Разработка», когда будете добавлять блоки модулей; список невозвращённых — `dev/analytics#samples-out`.
- **CRM (D723):** при передаче образца заказчику модель знает сделку (`DevModel.DealId`). Если дадите метод «добавить активность в сделку»
  (без прав CRM у вызывающего или с явной проверкой), запишем «образцы отправлены» в ленту сделки.
- **Производству (D761):** для плана-факта нужна фактическая себестоимость первых заказов изделия — дайте метод «факт затрат по
  производственному заказу» (материалы + работа), подключим в аналитику разработки.
- **Всем (переводы замечаний):** если сервис возвращает текст замечаний с подстановками — отдавайте шаблон и аргументы (`DevNote`),
  а шаблоны соберите в один список и зарегистрируйте в `TranslationCoverageTests` — иначе be/kk/uz увидят русский.

- **Всем (миграции, D770, ВАЖНО):** база вливает ветки сессий в любой момент — миграция, которую вы уже отправили (push) в свою ветку,
  может оказаться в базе раньше, чем вы её «поправите». Не пересоздавайте и не удаляйте отправленные миграции: только новая
  корректирующая. Проверка: `git ls-tree --name-only origin/claude/fervent-volta-3pn88r <путь к Migrations> | grep <имя>`. Путь обновления
  проверяйте так: скрипт базы на пустой БД, затем ваш полный идемпотентный скрипт дважды.
- **Базе:** при слиянии моей ветки удаление файла миграции из ветки «побеждает» (база файл не меняла) — если увидите в своей ветке
  удаление чужой уже применённой миграции, остановите слияние и напишите владельцу ветки.
